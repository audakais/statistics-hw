Hashing, key derivation and cryptographic primitives behind an Ethereum wallet.

01The pipeline

An Ethereum wallet is not one algorithm doing one job end to end. It is a chain of five independent primitives, each solving a different problem, wired together in a fixed order:

Four of these five arrows are one-way (mnemonic→seed, public key→address, address→checksum encoding); only secp256k1's own forward direction (private→public key) is reversed by the signature step later, when the wallet proves ownership without ever revealing the private key.

02Role of each primitive

BIP-39 — mnemonic sentence and seed generation

Takes 128–256 bits of entropy, maps it onto a fixed 2048-word list, and appends a checksum word derived from a hash of the entropy. The result is a sentence a human can write on paper, read aloud, or type back in without ambiguity. A PBKDF2 pass (with HMAC-SHA512, 2048 rounds) then stretches the mnemonic plus an optional passphrase into a 512-bit seed. BIP-39 is about usability for a secret, not about generating cryptographic randomness — the entropy has to already be random before BIP-39 ever sees it.

BIP-32 — hierarchical deterministic (HD) key derivation

Turns one seed into an entire tree of key pairs through repeated HMAC-SHA512 derivation steps, each producing a child private key and a chain code to derive the next level. One seed backup therefore recovers unlimited accounts and addresses, deterministically, without ever storing more than the seed. Without BIP-32 a wallet would need to generate and separately back up a new random key for every single address.

BIP-44 — standard derivation paths

BIP-32 defines how to derive a child key; BIP-44 defines which children to derive and in what order, via the path m / purpose' / coin_type' / account' / change / index. Ethereum wallets use m/44'/60'/0'/0/0 for the first account's first address. Without this convention, two wallets given the same seed could derive completely different addresses; BIP-44 is what makes a seed phrase portable between MetaMask, Rabby, a hardware wallet, and so on.

secp256k1 — elliptic-curve public-key cryptography

Treats the private key as a scalar k and computes the public key as the point Q = kG on a fixed elliptic curve, exactly the scalar multiplication explored in HMWK1 (same curve shape, real p is a 256-bit prime instead of 17). This is the only asymmetric step in the whole pipeline: it is what lets someone sign a transaction with a private key and lets anyone else verify that signature using only the public key, never the private key itself.

Keccak-256 — hash function used in address derivation

Compresses the 64-byte uncompressed public key down to a 32-byte digest; the Ethereum address is the last 20 bytes of that digest. A hash is the right tool here because an address only needs to be a short, collision-resistant, one-way fingerprint of the public key — there is no algebraic relationship to preserve, unlike the private-key-to-public-key step.

EIP-55 — mixed-case checksum encoding

Takes the 40 hex characters of an address, hashes the lowercase string with Keccak-256 again, and uses the hash's bits to decide, character by character, whether each hex digit should be upper- or lowercase. The address itself does not change; this only adds redundancy a client can check in milliseconds to catch a mistyped or corrupted address before funds are sent anywhere.

03Five different jobs, five different categories

It helps to separate what each step is, not just what it does:

Key derivation and public-key cryptography both involve "hard to invert" relationships, but for different reasons: BIP-32 derivation is hard to invert because it runs data through HMAC-SHA512 (hash-hardness); secp256k1 is hard to invert because of the ECDLP (a specific number-theoretic problem on that one curve). Conflating the two is the single most common mix-up when first reading this pipeline.

04Statistical properties, and why the comparison with HMWK1 matters

HMWK1's toy-curve experiment showed that Q = kG is deterministic and algebraically structured (Q(k+1) = Q(k) + G, and the whole sequence cycles with period equal to the subgroup order). Flipping a single bit of k does not reliably scramble every bit of Q the way it would for a hash — and it does not need to, because secp256k1's security rests on the ECDLP being hard, not on Q "looking random".

Keccak-256 is built for the opposite statistical profile on purpose: flipping a single input bit should flip roughly half of the 256 output bits with no predictable pattern (the avalanche property), and the 256-bit digest should look statistically indistinguishable from a random string for any structured input, including a 64-byte public key that was itself produced by a very non-random process (scalar multiplication). The checksum in EIP-55 only needs a much weaker property — that a typo almost always changes the hash, not that the hash is unpredictable under adversarial attack — which is why it is allowed to reuse Keccak-256 as a cheap source of "looks random enough to catch mistakes" bits rather than requiring its own dedicated error-correcting code.

So the same statistical tests used in HMWK1 (coordinate/bit distributions, correlation, avalanche) are diagnostic for very different reasons in each step of this pipeline: for secp256k1 they would at best show the algebraic structure is not hidden (which is fine — that was never the security argument); for Keccak-256 those same tests are a direct, meaningful check of whether the hash is doing its job.

05Historical and temporal context

1977RSA — first practical public-key cryptosystem, based on the hardness of factoring.
2001SHA-2 / SHA-512 — NIST standardises the SHA-2 family (FIPS 180-2), Merkle–Damgård construction.
2012BIP-32 — hierarchical deterministic wallets proposed (Pieter Wuille).
2013BIP-39 — mnemonic sentences for deterministic key generation.
2014BIP-44 — multi-account hierarchy for HD wallets; Ethereum itself goes live in 2015.
2015SHA-3 — NIST standardises SHA-3 (FIPS 202), based on the Keccak sponge construction.
2016EIP-55 — mixed-case checksum encoding for Ethereum addresses.

The ordering is not an accident: Ethereum's design (2013–2015) borrowed secp256k1 directly from Bitcoin and adopted Keccak before NIST had finished standardising SHA-3, which is exactly why it ended up with a slightly non-standard hash. BIP-39/32/44 were being finalised in the Bitcoin ecosystem at almost the same moment Ethereum was being designed, so Ethereum wallets reuse the same HD scheme rather than inventing a new one.

06SHA-2/SHA-512 vs. Keccak/SHA-3 — not the same thing

SHA-2 (2001) and SHA-3 (2015) are both NIST standards, but they are structurally unrelated: SHA-2 is a Merkle–Damgård hash built from a block cipher-like compression function, while SHA-3 is a sponge construction built around the Keccak permutation, chosen specifically because it does not share SHA-2's design (the 2007–2012 SHA-3 competition was triggered by theoretical attacks on Merkle–Damgård hashes, and NIST wanted a structurally different backup).

Keccak and SHA-3 are closer, but still not identical. Keccak was the submission that won the SHA-3 competition in 2012; when NIST finalised it as FIPS 202 in 2015, it added extra domain-separation bits to the padding (so that SHA3-256, SHA3-512 and the SHAKE variants can all share the same permutation without colliding). Ethereum's Keccak-256 was wired into the protocol in 2014–2015, using the original, pre-standardisation Keccak padding — so Keccak-256("abc") and the standardised SHA3-256("abc") are two different 32-byte digests for the same input, even though both run the same underlying permutation. Every "keccak256" function in Solidity and in Ethereum client code means the original Keccak, never NIST's SHA3-256.

08Why not just use one algorithm for everything?

Each primitive in the pipeline is answering a question none of the others can answer:

  • BIP-39/32/44 → key management. The question is "how do I back up and organise many keys from one secret?" This has nothing to do with cryptographic hardness; it is a usability and bookkeeping problem, solved with deterministic derivation (HMAC-SHA512 used purely as a good pseudorandom function, not for any hashing property).
  • secp256k1 → ownership and signatures. The question is "how does someone prove they control a key without revealing it?" Only an asymmetric primitive with a hard inversion problem (ECDLP) can answer that; no hash function can substitute for a digital signature scheme.
  • Keccak-256 → compression and fingerprinting. The question is "how do I get a short, fixed-size, collision-resistant identifier from an arbitrary-size public key?" That is exactly what a hash is designed for, and nothing else in the pipeline is.
  • EIP-55 → error detection. The question is "how does a human catch a typo before sending funds to the wrong address?" This needs redundancy that is cheap to verify, not cryptographic strength against an adversary — which is why it is allowed to just reuse Keccak-256 rather than needing its own primitive.

Using one algorithm for all four jobs would mean picking a tool that is simultaneously great at being reversible-by-design (derivation), irreversible-by-hardness (signatures), irreversible-by-collision- resistance (hashing), and cheaply-redundant (checksums) — properties that are partly in direct tension with each other. Composing specialised primitives, each independently replaceable (as happened when Ethereum could in principle swap Keccak for SHA-3 without touching secp256k1 or BIP-32), is a more robust engineering choice than one monolithic algorithm would ever be.

09Hands-on notes

I installed MetaMask and created a throwaway test wallet (no real funds) to check some of the claims above against an actual client instead of just the spec.

Derivation path. I went looking for the BIP-44 path (m/44'/60'/0'/0/0) under "Account details" and "Show private key", expecting to see it printed somewhere next to the key. I didn't find it anywhere in the normal UI — MetaMask will export the raw private key, but it does not surface the derivation path itself to the end user. That is a useful data point on its own: BIP-44 is working under the hood (the key clearly came from somewhere in a deterministic tree, since the wallet can regenerate every account from the same seed), but the wallet treats the path as an implementation detail, not something a normal user is expected to ever see or care about.

Checksum, verified against my own implementation. My test account's address, exactly as MetaMask displays it, is:

0xeDda9A3c677A14379Bd645f731c443551Eade4f2

I ran this same address (lowercased) through the EIP-55 tool built for section 7 of this page, and the capitalisation it computed matched MetaMask's version character for character. That is a small but concrete confirmation that the Keccak-256 implementation above — written from the specification, not copied from a library — actually agrees with a real wallet's output, not only with Node's built-in SHA3-256 test vectors.

Checksum, broken on purpose. I took my own address and flipped one letter's case (0xeDda... → 0xEDda..., first character only), which should fail EIP-55 validation — a correctly-checksummed address would never have that exact capitalisation. I pasted it into MetaMask's "Send" recipient field: no warning, no error, nothing. MetaMask accepted it as a normal destination with no visible difference from a valid address.

That is a more interesting result than a clean confirmation would have been. Section 2 describes EIP-55 as something that lets "a client catch a mistyped or corrupted address before funds are sent anywhere" — and that is true of the specification, but my own test shows it is not necessarily true of a given client's UI. The checksum is only useful if whatever software is reading the address actually bothers to verify it and surface a warning; nothing in the protocol forces that. A capitalisation typo that happens to still be 40 valid hex characters will go to whatever address those hex digits decode to, silently, at least in the version of MetaMask I tested. The cryptographic design is sound; whether it protects a user in practice depends entirely on whether someone implemented the check in the client.

Second wallet, for comparison: Rabby. I installed Rabby separately (a different, independent test wallet, not an import of the MetaMask one) to see whether the two points above are MetaMask quirks or general to EVM wallets. Its address:

0xE0553F3f3C22248D1190CDe7138A0483d6caB4A0

Checked against the same from-scratch EIP-55 tool: matches character for character again — two independent wallets now agree with this page's own Keccak-256 implementation, which is a stronger check than one coincidence would have been.

On the derivation path, Rabby behaves the same as MetaMask: digging through address management only ever surfaces the address itself, never the m/44'/60'/0'/0/0 path. So that is not a MetaMask-specific choice to hide implementation detail — it looks like a shared convention across mainstream wallet UIs, presumably because the path is genuinely irrelevant to a user who only ever uses the first default account.

The checksum test is where the two wallets disagree, and this is the sharpest finding of the whole section. Pasting the exact same kind of single-letter-case-flipped address that MetaMask accepted silently, Rabby's "Send" screen immediately rejected it with "This address is invalid". Same EIP-55 standard, same kind of broken input, opposite outcomes. That settles the question raised above: EIP-55 enforcement is not guaranteed by the standard, it is a per-client implementation choice — and in this small, informal test, Rabby implements the safety net the specification was designed to provide, and the version of MetaMask I used does not.
