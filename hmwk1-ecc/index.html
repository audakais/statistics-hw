5. Discussion — one-way function vs. hash function

Both k → Q = kG and a hash function H are easy forward, hard backward, and deterministic. That is where the similarity ends.

  • Structure. Q = kG is algebraic: Q(k+1) = Q(k) + G exactly, always. A hash function has no such relation — H(k+1) has nothing predictable in common with H(k). The periodicity table above (k and k + 9 landing on the same point) is only visible because the toy subgroup is tiny; on real secp256k1 the subgroup order n is a 256-bit prime, so the same relation holds but no human will ever see two k values collide.
  • Avalanche effect. Flipping one bit of k can send Q anywhere in the subgroup (the double-and-add path changes completely), but incrementing k by 1 only ever shifts Q by a fixed G. A cryptographic hash is designed so that every single-bit change in the input looks like a bit-flip test, with no exceptions and no structure to exploit — that guarantee is the explicit design goal of a hash function, not of EC scalar multiplication.
  • Why the one-way property still holds. Security does not come from Q "looking random" statistically. It comes from the ECDLP: there is no known sub-exponential algorithm to recover k from Q = kG on a well-chosen curve. The hardness is a number-theoretic, structural property of the group, independent of whether the output coordinates pass a uniformity test.
  • What the statistics above actually show. Coordinate "uniformity" over a full cycle of a cyclic subgroup is a byproduct of group theory (every element of the subgroup gets visited once per cycle), not evidence of cryptographic strength. Bit-frequency and avalanche tests are the right tool for judging a hash function (that is exactly what HMWK2 uses Keccak-256 for); they are the wrong tool for judging an asymmetric primitive like secp256k1, whose security argument is purely algebraic.
