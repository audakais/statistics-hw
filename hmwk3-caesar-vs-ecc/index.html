Caesar cipher vs. a toy ECC scheme

The same short message encrypted twice: once with EC-ElGamal on secp256k1 with a deliberately small private key, once with the Caesar cipher. Then both get attacked: the Caesar cipher with letter statistics, the ECC scheme by searching its small key space.

01Toy ECC scheme: encrypt and decrypt

In HMWK1 the scalar multiplication Q = kG was done on y² = x³ + 7 over a field of 17 elements, so every point could be drawn. Here the same functions (pointAdd, double-and-add) run on the real secp256k1 parameters: p and the group order n are 256-bit numbers and G is the standard generator. The only toy element is the private key, which is drawn from [1, 2b] with b around 20 instead of from [1, n−1]. That keeps the attack in section 06 fast enough to run inside this page.

A public key on its own does not encrypt anything, so on top of it I used EC-ElGamal:

  1. Public parameters. The curve y² = x³ + 7 mod p, the generator G and its order n. Everyone knows these and they are the same for every user.
  2. Key generation (receiver). Choose the private key k at random in [1, 2b] and publish Q = kG. Computing Q from k takes about b doublings; going back from Q to k is the discrete logarithm problem.
  3. Encoding. The message is turned into UTF-8 bytes, and each byte v becomes the point M = (v + 1)G. The +1 is there because v = 0 would otherwise map to the point at infinity. The receiver decodes by looking M up in a table of the 256 possible points. This is a discrete log too, but only over 256 values, so it is cheap.
  4. Encryption (sender, uses only Q). For every byte, pick a fresh random r in [1, n−1] and send the pair C1 = rG, C2 = M + rQ. The point rQ is a one-time mask that hides M, and C1 carries just enough information for the receiver to rebuild that mask. r is thrown away right after.
  5. Decryption (receiver, uses k). kC1 = k(rG) = r(kG) = rQ, so C2 − kC1 = M. Look M up in the table to get the byte back.

Role of the keys. The scheme is asymmetric. Q is enough to encrypt but useless for decrypting, so it can be published. k is the only thing that removes the mask, and the sender never needs it. The per-block r is a third, short-lived secret: anyone who learns r for a block can compute rQ and read that block, which is why it must be fresh and random every time (section 07 shows what happens if it is not).

02Caesar cipher on the same message

Number the letters A = 0, …, Z = 25. With key s ∈ {0, …, 25}:

encryption y = (x + s) mod 26 decryption x = (y − s) mod 26

Upper and lower case are shifted separately and everything that is not a letter (spaces, digits, punctuation) is copied unchanged, which is the usual textbook convention. There is a single key and both sides need it, so this is a symmetric cipher: whoever can encrypt can also decrypt.

03Similarities and differences

Seen from far enough away, both schemes do the same thing: they add a secret value to the plaintext inside a group and subtract it again to decrypt. Caesar adds s in the integers mod 26; EC-ElGamal adds the point rQ in the group of curve points. The important difference is how often that value changes. Caesar adds the same s to every letter. EC-ElGamal adds a new rQ to every byte, and almost every difference in the table below follows from that.

Statistical properties. A Caesar ciphertext has exactly the same letter histogram as its plaintext, only moved s positions to the right. Measures that do not care about which letter is which, like the index of coincidence, do not change at all. With EC-ElGamal the repeated letters of the message turn into unrelated points, so counting ciphertext blocks reveals nothing about the plaintext distribution. The one thing it does reveal is the length: one block per byte. The numbers below are computed from the message in section 01.

04Statistical cryptanalysis of the Caesar cipher

Corpus. The reference statistics come from the full text of Jane Austen's Pride and Prejudice (Project Gutenberg #1342, licence header and footer removed). The script tools/build-corpus.js counts single letters, letter pairs and letter triples (case ignored, non-letters dropped) and the 1000 most common words. The test messages are taken from a different book, Dickens' A Tale of Two Cities (#98), so the method is never tested on the same text it learned from.

reference letter distribution (training corpus)

Algorithm. There are only 26 keys, so they can all be tried. The real question is how to recognise the right decryption automatically. I compared four rules:

  1. Most frequent letter. No search at all: assume the most common ciphertext letter is E (the most common corpus letter), so s = (top letter − E) mod 26. This is frequency analysis in its crudest form.
  2. Chi-squared. For each candidate s, decrypt, count the letters Oi and compare them with the counts expected from the corpus, Ei = N·pi:
    χ²(s) = Σi (Oi − Ei)² / Ei key = argmin χ²(s)
    This uses the whole histogram instead of only its maximum.
  3. Dictionary words. Plain exhaustive key search: decrypt with each s and count how many words belong to the 1000 most frequent corpus words. Keep the s with the most hits.
  4. Trigram scoring. For each s, add up the log-probabilities of every three-letter window of the decrypted letter stream, using the corpus trigram counts with add-one smoothing (otherwise a single unseen trigram would give log 0):
    score(s) = Σj log P(xj xj+1 xj+2) key = argmax score(s)
    This looks at the order of the letters, not just how many of each there are.

All of them cost about 26 × (text length) operations, which is nothing. The only real difference between them is how much information about English each one uses.

05Effectiveness vs. ciphertext length

For each length L (counted in letters), the experiment draws 1000 random passages from A Tale of Two Cities that start at the beginning of a word, encrypts each one with a random key from 1 to 25, and checks whether each method gets that key back. The random generator is seeded (seed 2024), so the table is the same every time the page is loaded and matches node tools/experiments.js. The second option removes spaces and punctuation before encrypting, which is how classical ciphertexts were usually written down.

What the results show (the numbers quoted here are from the default run, with spaces):

  • Most frequent letter is clearly the weakest. It is right only 20.4% of the time at 10 letters, 61.5% at 100 and 93.1% at 500. E is the most common letter (12.9% in the corpus), but T is at 8.7% and A, O, I, N are all around 7%, so in a short passage E is often not on top. One unlucky count is enough to get a wrong key.
  • Chi-squared uses all 26 frequencies at once, so the error in one count is compensated by the others. It reaches 78.9% at 10 letters, 94.6% at 20 and is always right from 50 letters on.
  • Dictionary search works better than chi-squared on short texts (86.3% at 10 letters) because a word like "the" or "and" is a very strong signal. But it depends completely on word boundaries: with spaces removed it drops to 0.2% at 10 letters and 0% from 15 on.
  • Trigram scoring is the best at every length: 82.3% at 5 letters, 98.5% at 10, and 100% from 20 letters on. It does not need spaces, so its results are the same in both modes. The order of the letters carries much more information than their counts: English allows "THE" but almost never "QZK".

Limitations.

  • Short messages. Below 10–15 letters there is simply not enough text for the statistics to point to one key. For 3 letters even the trigram method is right only 61.8% of the time. But even when the top guess is wrong, the correct key is usually near the top of the ranking, and with only 26 candidates a person can just read them.
  • Texts that do not look like the corpus. The examples menu in section 04 contains a few. "Fuzzy jazz buzz" (letters that are rare in English) fools every method. "A lazy fox jumps quickly" is recovered only by the trigram method. A string with no repeated or common letters, like "XYZ QRS KJV", gives no usable signal to any of them.
  • The wrong language. The model is English-only. In the examples, an Italian sentence is still broken by chi-squared and trigrams, because Italian letter frequencies are close enough and the attack only has to pick the best of 26 shifts, not match the distribution exactly. The dictionary method fails there, since Italian words are not in the English list.
  • Probabilistic output. The attack gives the most likely key, not a proof. With a long text this hardly matters, but for a short one there is no way to be sure from statistics alone. This is different from the ECC attack in section 06, where a candidate key can be checked exactly.

Comparing the approaches. Exhaustive key search and frequency analysis are not really alternatives for Caesar. With 26 keys, trying all of them is always possible, and the statistics are only the rule that picks the right one. The baseline "most frequent letter = E" is the only method that avoids the search, and it is also the worst. Among the search-based rules the ranking is clear: unigram statistics (χ²) < whole words < trigrams, with the dictionary dropping out completely when there are no spaces. More context in the score means fewer letters are needed.

06Attacking the toy ECC scheme

The attacker knows the curve, G, the public key Q, the ciphertext, and that k ≤ 2b. The ciphertext statistics are useless here (section 03), but the key space is small, and that is enough. Three ways to use it:

  1. Exhaustive search on the public key. Compute G, 2G, 3G, … by adding G each time and stop when the point equals Q. That is at most 2b additions. To make each step cheaper I keep the running point in Jacobian coordinates (X, Y, Z) ↔ (X/Z², Y/Z³). Adding G then needs no modular inverse, and comparing with Q costs only two multiplications (X = QxZ², Y = QyZ³). The benchmark below shows how much faster this is than the affine formula.
  2. Exhaustive search from the ciphertext only. Without using Q: for each candidate k, compute C2 − kC1 for the first block and check whether it is one of the 256 message points. This is the ECC version of the Caesar dictionary test, but the test is almost perfect: for a wrong k the result is essentially a random point, and the chance that it lands in a 256-element table is about 256/n ≈ 2−248. This version needs the affine x coordinate at every step for the lookup, so it is slower.
  3. Baby-step giant-step. Write k = i·m + j with m = ⌈√2b⌉. Store the x coordinates of jG for j = 0..m−1 (baby steps), then compute Q − i·mG for i = 0, 1, … (giant steps) until one of them is in the table. That takes about 2·2b/2 additions and 2b/2 stored points, so roughly the square root of the exhaustive search.

07Discussion

the two attacks compared

  • What is exploited. The Caesar attack exploits redundancy in the plaintext. English is far from random, and the cipher passes that structure through to the ciphertext. The ECC attack does not use the plaintext at all. It exploits the fact that the key comes from a small set. The ciphertext gives away no statistics because of the fresh r.
  • What the attacker needs. The Caesar attack needs ciphertext, and enough of it (section 05). Attack 1 on ECC needs only the public key, so it works before any message has even been sent, and once k is found every past and future message can be read. The length of the message does not matter.
  • How sure the result is. Statistics give the most probable key and can be wrong on short or unusual texts. In the ECC case a candidate is checked exactly (kG = Q, or C2 − kC1 lands in the table), so when the search finds a key it is the right one.
  • Cost. Caesar costs 26 trials no matter what, so the key space never protected it. The ECC attack grows with the key space: 2b for the plain search, about 2b/2 for BSGS. Every extra key bit doubles the plain search time.

why this does not work against real ECC

A properly generated secp256k1 key is uniform in [1, n−1] with n ≈ 2256. Plain search would need about 2256 additions. The best known algorithms for the discrete log on a well-chosen curve are the generic ones (BSGS, Pollard's rho), and they need on the order of √n ≈ 2128 operations. BSGS would also have to store about 2128 points. The extra structure of secp256k1 (the negation map and its efficient endomorphism) only speeds up rho by a small constant factor, at most √6. It does not change the exponent. The last rows of the table in section 06 show what 2128 means at realistic speeds. This is why a 256-bit curve is said to give "128-bit security". The attacks in section 06 are exactly the ones that would be used on a real key, and they work here only because b is tiny. Everything that made them easy came from the toy restriction, not from the curve.

alternative attacks

  • Pollard's kangaroo (lambda) method is designed for a key known to lie in an interval of width w. It needs about 2√w operations like BSGS, but almost no memory, and it parallelises well. For a bounded key it would be the practical choice once the BSGS table no longer fits in memory: for b = 80 the table would hold 240 points, which at 32 bytes per x coordinate is about 35 TB.
  • Pollard's rho is the memoryless generic method for the full group. It is the reason real keys are 256 bits and not 128.
  • Precomputation and multiple users. One BSGS table of jG serves every public key ever made with the same small bound, so attacking 1000 users costs little more than attacking one. With 2b possible keys and b = 20, two users get the same key with probability 50% once there are about 1.18·√220 ≈ 1200 users (birthday bound), and this is visible from the public keys alone.

which weaknesses come from the key space, and which from the design

Everything above (exhaustive search, BSGS, kangaroo, shared tables, key collisions) comes from the restricted key space. It goes away with a full-size k. The way I built the toy scheme also has problems that would remain even with a 256-bit key. Two of them are demonstrated live:

  • Reusing r. If the same r is used for all bytes, C1 is identical in every block and C2i = Mi + S with the same mask S = rQ everywhere. Equal bytes then give equal C2, so the scheme becomes a substitution cipher on bytes, with a fixed additive mask just like Caesar. The attack from section 04 applies again: guess that the most frequent C2 is a space, compute S = C2 − 33G, and subtract S from everything. The whole message comes out without k ever being found, whatever its size.
  • Malleability. Adding G to every C2 produces a valid ciphertext of the message with every byte increased by 1, a Caesar shift on bytes done by someone who does not know any key. There is no integrity check that could detect it.
  • Independent blocks. Every byte is a separate ciphertext, so blocks can be dropped, repeated or reordered without detection, and the exact message length is visible.
  • Bad randomness for r. If r came from a small or predictable range, the attacker could search for r from C1 = rG with the same methods as in section 06 and get M = C2 − rQ, again without k. A small k and a small r are the same mistake.
  • Efficiency and implementation. 66 bytes of ciphertext per byte of message. The code also branches on the key bits in double-and-add and uses variable-time BigInt arithmetic, which is fine for a toy but would leak timing information in a real implementation. Real systems use ECC only to agree on a key (ECDH, as in ECIES) and then encrypt the message with a symmetric authenticated cipher. That fixes the expansion, the malleability and the block structure together.
